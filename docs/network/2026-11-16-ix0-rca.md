# RCA: ix0 to switch24a Te1/0/27 remote faults after the DAC swap

Date: 2026-11-16. Status: root cause not yet isolated. Nothing was changed.

All data below comes from read-only checks. Raw files are in `docs/network/evidence/2026-11-16-ix0/`.
Each claim names its evidence file. An unproven idea is marked as a hypothesis.

## 1. Summary

1. The faults continue after the media change. The old link used an SR optic and LC fibre. The new link uses a 1 m passive DAC.
2. Both devices rebooted within 36 seconds of each other on 2026-11-11. The faults returned anyway.
3. The DAC did lower the user-visible packet loss. It did not stop the remote faults.
4. The evidence does not show a configuration mismatch that can cause these faults.
5. The remaining common parts are the pfSense `ix0` SFP+ port, the switch `Te1/0/27` SFP+ port, and how the two interact.
6. No single part is proven faulty. A controlled swap test is the next step (section 7).

### 6a. MTU test (`mtu-checks.txt`, 2026-11-16 21:35 UTC)

The switch ports use MTU 9216. pfSense `ix0` uses 1500. Proxmox and dockermaster use 1500 on every checked interface.

A mismatch drops frames above 1518 bytes. pfSense counts them as oversized frames.
The `recv_oversized` counter stayed at 13 over 60 seconds. It did not grow.

I sent 300 pings with the do-not-fragment flag at 1500 and at 1428 bytes to two targets. Loss was 0.7 to 1.3 percent at both sizes.
Loss did not depend on size, so the 1500-byte limit does not drop these packets.

An MTU mismatch cannot create remote faults. Those are signalled below the frame layer.
Limit: I did not check the MTU of every host. I did not test jumbo-frame hosts such as the NAS.

`inventory/servers.md` says Proxmox `vmbr10` uses MTU 9000. Live, it uses 1500. The inventory is out of date or the setting was lost.

The switch cannot split its input errors by type. The RMON table is empty. The TP-Link private MIB shows only utilisation.
Omada returns no events and no alerts for the site.
The pfSense system log has no MTU, oversize, or fragment messages.

pfSense counters since boot: 70,342 datagrams fragmented, 0 that failed to fragment, and 64,765 output packets dropped for lack of buffers.
I found no MSS clamp in the pfSense config.
The switch sends syslog to `192.168.1.50:514`. The NAS listens there. Only the `log` group can read its log file, so I was denied access.

Remote faults are a physical-layer signal. VLAN, MTU, flow control, and spanning-tree settings act above that layer.
The evidence therefore does not support a configuration mismatch as the cause of the faults.
Two items drifted from the June design. Fix them as hygiene. They are VLAN 1 on the trunks and the flow-control setting.

Limit: Omada shows intent. The live switch VLAN table returned no data over SNMP (`switch-vlan-membership-snmp.txt`).
I did not read the switch CLI. The switch access list blocks SSH.

## 7. Hypotheses and tests

| # | Hypothesis | For | Against | Test |
|---|---|---|---|---|
| H1 | The `ix0` port on the pfSense side has a signal problem on its transmit lane | Fault survived two media types. Direction is pfSense transmit | Cannot tell it from the switch receive side | Move the DAC to `ix1`. See below |
| H2 | The switch `Te1/0/27` receive side has a signal problem | Port 25 also shows errors. Both faulty ports share one switch | Ports 26 and 28 are clean. Port 25 is a different link | Connect a different device to `Te1/0/27` |
| H3 | This pfSense and switch pair does not tune well with third-party cables | Cable has a Mellanox ID. Neither vendor lists it as tested | The optic also failed | Try a cable tested by Netgate or TP-Link |
| H4 | A shared power or ground problem | Both devices rebooted together on 2026-11-11 | No power data. Someone may have power-cycled both by hand | Read the UPS and outlet logs |
| H5 | A configuration mismatch | Flow control and VLAN 1 differ | Section 6 | Not worth testing first |

I give no probability for each. The data cannot support honest numbers.

Tests that need your approval. Each one drops the LAN trunk for about 30 to 50 seconds. Run them in a maintenance window.

1. Move the DAC from `ix0` to `ix1`. Re-parent the four VLANs to `ix1`. Watch `Te1/0/27`. If the faults stay, the switch side is more likely. If they stop, the `ix0` port is the cause.
2. Replace the DAC with a cable on the Netgate or TP-Link tested list. If you want the lowest-effort test, do this one first.
3. Attach a different known-good device to the switch `Te1/0/27` port. This needs a free port path, so plan it with the `lagg0` work.

Rollback for each test: restore the cable to `ix0` and the VLAN parent. Set the `nobounce` flag first.

## 8. Corrections to earlier statements

1. I said the NIC subsystem ID `ffff:ffff` was unusual. The inventory lists a Netgate 8200 (unconfirmed). An onboard NIC often has a blank ID. I withdraw that point.
2. I said a flow-control mismatch was "a real configuration difference". It is a real difference. The counters show it has no effect.
3. The repo notes and the watchdog log say "replace the optic". That is out of date. The link now uses a DAC (installed 2026-11-11). The text is wrong.
